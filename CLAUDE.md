# Инструкции проекта

Это тестовое задание для собеседования. Код будут читать и оценивать, поэтому качество важнее скорости.
Пиши так, как написал бы сильный senior-разработчик: просто, понятно, без лишнего.

## Главное правило: без костылей

- Никаких временных обходов, хаков, «потом поправим», закомментированного кода, `// TODO: fix`, подавления
  ошибок (`@ts-ignore`, `# type: ignore`, `eslint-disable`, `catch {}`), магических задержек и ретраев
  вместо понимания причины.
- Если текущая структура мешает сделать правильно — меняй структуру. Переделать модуль лучше,
  чем подпереть его.
- Нашёл причину бага — исправляй причину, а не симптом.
- Если правильное решение заметно больше по объёму или меняет архитектуру — сначала коротко опиши
  его и спроси, потом делай.

## Актуальная документация

- Перед использованием любой библиотеки, фреймворка или API сверяйся с актуальной документацией
  (Context7, затем официальный сайт). Не пиши по памяти: API меняются.
- Используй текущие стабильные версии зависимостей; фиксируй версии в lock-файле.
- Не используй deprecated API. Если документация предлагает новый рекомендуемый способ — используй его.

## Архитектура и расширяемость

- Чёткое разделение слоёв: предметная логика отдельно от транспорта (HTTP/CLI/UI), хранения и внешних
  сервисов. Бизнес-логика не знает о фреймворке.
- Зависимости передаются явно (DI через конструктор/параметры), без глобального состояния и синглтонов.
- Зависимость направлена внутрь: внешние слои зависят от внутренних, не наоборот.
- Точки расширения — через интерфейсы/абстракции там, где реально ожидается вариативность
  (хранилище, внешние API, способы доставки и т.п.). Не создавай абстракции «на всякий случай» — YAGNI
  важнее, чем выдуманная гибкость.
- Конфигурация — через переменные окружения/конфиг-файл с валидацией при старте. Никаких захардкоженных
  URL, ключей, портов.
- Одна ответственность на модуль/класс/функцию. Если функцию трудно назвать — её надо разделить.

## Качество кода

- Строгая типизация (strict-режим компилятора/тайпчекера). Никаких `any` без веской причины.
- Явная обработка ошибок: доменные ошибки отдельными типами, понятные сообщения, корректные коды ответов.
  Ошибки не глотаются.
- Валидация всех входных данных на границе системы.
- Понятные имена вместо комментариев. Комментарии — только чтобы объяснить «почему», не «что».
- Без дублирования: общее выносится, но только когда это действительно одно и то же понятие.
- Линтер и форматтер настроены в проекте и проходят без ошибок и предупреждений.

## Тесты

- Unit-тесты на бизнес-логику, интеграционные — на ключевые сценарии (API, БД).
- Тесты проверяют поведение, а не детали реализации.
- Каждый исправленный баг — с тестом, который падал до исправления.
- Перед тем как сказать «готово», запусти тесты, линтер и тайпчекер. Если что-то падает — скажи об этом прямо.

## Безопасность

- Секреты только через окружение; `.env` в `.gitignore`, в репозитории — `.env.example`.
- Параметризованные запросы к БД, экранирование вывода, проверка прав доступа.

## Проект как продукт для ревьюера

- `README.md`: что сделано, как запустить (одной-двумя командами), как запустить тесты, принятые
  архитектурные решения и компромиссы, что можно улучшить.
- Если уместно — Docker / docker-compose для запуска без ручной настройки окружения.
- Git: маленькие осмысленные коммиты с понятными сообщениями (Conventional Commits).

## Процесс работы

1. Прочитай задание целиком, выпиши требования и неясности. Неясное — спроси, не додумывай молча.
2. Предложи структуру проекта и ключевые решения до написания кода.
3. Реализуй по шагам, каждый шаг — рабочее состояние с тестами.
4. В конце — ревью собственного кода как чужого: что бы сказал придирчивый ревьюер?

## Стек и команды

- Node.js ≥ 24 (целевой 26 LTS), TypeScript 6.0 (strict), ES modules. Запуск `.ts` напрямую через нативный
  type stripping Node — без сборки. Только стираемый синтаксис: без `enum`, parameter properties, `namespace`.
- HTTP — встроенный `fetch`; тесты — `node:test`; аргументы — `node:util` `parseArgs`. Новые зависимости
  в рантайм не добавлять без веской причины.
- Команды: `npm start -- <url>`, `npm test`, `npm run lint`, `npm run typecheck`, `npm run format`.
- План и методика замера — в `PLAN.md`.
